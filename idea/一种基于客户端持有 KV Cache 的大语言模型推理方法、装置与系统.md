## 二、背景技术

### 2\.1 KV Cache 在 LLM 推理中的作用

在基于 Transformer 架构的大语言模型自回归推理过程中，为避免每生成一个新 token 都重新计算历史 token 的 Key/Value 张量，业界普遍采用 KV Cache 机制，将已计算的 K、V 张量缓存于显存（HBM）中以供后续解码步骤复用。KV Cache 大小与 batch size、序列长度、层数、KV 头数、单头维度成正比，在长上下文推理场景下常常成为显存与带宽的主要瓶颈。

### 2\.2 现有 KV Cache 管理方案及其局限

现有 KV Cache 优化方案沿着以下几条路线演进，但全部将 KV Cache 的存储与生命周期管理限制在**服务端集群内部**：

1. **服务端 GPU 内前缀缓存**：vLLM 的 PrefixCache、SGLang 的 RadixAttention 等方案将前缀 KV Cache 保留于 GPU HBM 中，供后续同前缀请求复用。局限：GPU 显存有限，LRU 淘汰频繁，缓存生命周期短（秒\~分钟级）。

2. **服务端分层存储**：SGLang HiCache 引入 L1（GPU）→ L2（CPU DRAM）→ L3（Mooncake / 3FS 分布式存储）三级缓存架构，将有效容量扩展至 TB 级。局限：仍然是服务端集群资产，跨天/跨周复用不可能，且带来复杂的运维成本。

3. **服务端间稀疏加载**：SGLang HiSparse 针对 DeepSeek Sparse Attention（DSA）架构，将全量 KV 存于 CPU pinned memory，GPU 仅维护 top\-k 热 buffer，配合 PD 分离通过 RDMA 从 Prefill 节点直接写入 Decode 节点的 host pool。局限：稀疏发生在服务端节点内部，客户端不可见、不可控。

4. **服务端间 KV 压缩流式传输**：CacheGen 将 KV Cache 视为流媒体，利用 token 间局部性、分层敏感度差异、算术编码，将 KV 压缩为紧凑比特流，在服务器节点间传输。局限：传输边界仍在数据中心内部，客户端仍需以文本 prompt 重新触发 Prefill。

### 2\.3 现有技术共同存在的技术问题

上述方案共同存在以下技术问题：

- **问题一**：KV Cache 生命周期完全由服务端策略决定，客户端无法感知其存在状态；一旦服务端淘汰，客户端只能被动等待重新 Prefill，造成 TTFT（Time\-To\-First\-Token，首 token 延迟）不可预测；

- **问题二**：KV Cache 长期存储受服务端资源与运营策略约束，跨会话、跨天、跨设备的长期复用几乎不可能；

- **问题三**：用户上下文对应的 KV Cache 表征长期驻留于服务提供方，在数据主权、合规审计、跨云迁移等场景形成事实上的 vendor lock\-in；

- **问题四**：客户端与服务端之间的每次请求都需重新上传全量 prompt，服务端需重新做完整 Prefill 计算，网络与算力成本高。

### 2\.4 使该问题可解的新技术前提

近期发布的 DeepSeek V4\-Flash / V4\-Pro 等模型采用 CSA（Compressed Sparse Attention，4× 压缩 \+ 稀疏检索）\+ HCA（Heavily Compressed Attention，128× 重度压缩）\+ SWA（Sliding Window Attention）的混合注意力架构，将 KV Cache 体量大幅压缩：1M token 上下文下 KV Cache 从 V3\.2 的水平进一步压缩至约 10%（V4\-Pro）乃至 7%（V4\-Flash）。这使得 KV Cache 的体量首次进入"可跨广域网络传输"的工程可行区间，为本发明提供了技术前提。

## 三、发明目的

针对现有技术中 KV Cache 由服务端独占管理所导致的生命周期不可控、长期复用困难、数据主权受限、上行冗余等问题，本发明的目的在于提供一种基于客户端持有 KV Cache 的大语言模型推理方法、装置与系统，通过将 KV Cache 的存储与生命周期管理转移至客户端，并在推理请求中以稀疏或差分方式按需上传，实现：

1. KV Cache 的跨会话、跨天、跨设备长期存储；

2. 客户端对 KV Cache 生命周期的完全感知与主动控制；

3. 上行链路的稀疏化与差分化，显著降低传输开销；

4. KV Cache 表征的数据主权归属于用户；

5. KV Cache 表征与具体推理引擎解耦，具备跨引擎、跨服务商可移植性。

## 四、发明内容

### 4\.1 技术方案概述

本发明提出一种**客户端持有 KV Cache（Client\-Held KVCache, 以下简称 CHK）**的大语言模型推理方法、装置与系统。其核心构思为：

- 服务端在完成一次推理请求的 Prefill 阶段后，将该请求上下文对应的 KV Cache 编码为**可携带 KV 表示（Portable KV Blob, PKB）**并返回客户端；

- 客户端将 PKB 及其元数据持久化于本地存储；

- 服务端在返回后不承担对该 KV Cache 的长期保管义务，可立即释放相关显存与内存资源；

- 在后续同上下文请求中，客户端基于本地维护的稀疏索引对 KV 块进行 top\-k 选择或差分编码，将所选子集随请求上传；

- 服务端接收后完成完整性校验、解码、张量重建，并结合稀疏补齐机制（miss\-and\-fill）进入 Decode 阶段。

### 4\.2 系统架构

本发明的系统包括客户端子系统与服务端子系统两大部分。

**客户端子系统包括**：

- **CHK 存储模块（CHK Store）**：以 IndexedDB、SQLite、本地文件或端侧 NPU 存储为载体，持久化保存 PKB 二进制数据及其元数据（模型标识、层结构描述、token 范围、内容哈希、TTL 等）；

- **生命周期管理模块（Lifecycle Manager）**：维护每个 KV Cache 条目的状态机（FRESH → USED → STALE → EVICTABLE → EVICTED），依据访问频次、TTL、用户策略、隐私窗口等策略触发状态转换；

- **稀疏选择模块（Sparse Selector）**：基于本地保存的 Indexer KV 快照，对当前 query 相关的 KV 块进行本地打分并选出 top\-k；

- **差分编码模块（Delta Encoder）**：基于上一次快照对本次上传的 KV 块进行差分与压缩；

- **安全签名模块（Attestation）**：执行 AEAD 加密与 HMAC 完整性签名；

- **传输模块**：以 HTTP/2 或 gRPC 多部分请求方式将 prompt、KV manifest、KV blob 上传至服务端。

**服务端子系统包括**：

- **完整性校验模块**：验证 KV blob 的 AEAD 与签名；

- **PKB 解码模块**：反量化、反算术编码、恢复原始 KV 张量；

- **KV 注入模块**：将恢复的 KV 张量灌入推理引擎（vLLM / SGLang / TensorRT\-LLM 等）的 KV pool；

- **补齐调度模块（Miss\-and\-Fill Scheduler）**：检测 Decode 阶段实际 attention 打分与客户端上传 top\-k 的偏差，动态请求客户端补传或本地重算缺失块；

- **可选反馈模块**：将 Decode 阶段新生成 token 的 KV 增量作为 delta 返回客户端。

### 4\.3 关键实施例

#### 4\.3\.1 可携带 KV Cache 表示（PKB）编码

PKB 采用与 DeepSeek V4 分层压缩兼容的格式：

- **C4A 主 KV**：形状为 \[S/4, 512\]，用于中距离压缩块；

- **C128A 主 KV**：形状为 \[S/128, 512\]，用于远距离重度压缩块；

- **Indexer KV**：形状为 \[S/4, 128\]，作为客户端本地稀疏打分的降维索引；

- **SWA 部分不上传**：滑动窗口部分由服务端从最近 token 直接重建。

在此基础上，参考 CacheGen 的编码思想：

- 每 10 个 token 为一组，仅存 anchor 及其余 token 的 delta；

- 分层量化：浅层量化 bin 更细（如 32 bin），深层量化 bin 更粗（如 8 bin）；

- 按 layer × channel 分组做算术编码，逼近熵极限；

- 每个 chunk 独立可解码，支持流式增量上行。

#### 4\.3\.2 客户端稀疏选择流程

客户端稀疏选择的关键在于：**在不进行完整前向计算的前提下预判 top\-k**。本发明利用 DeepSeek V4 的 Lightning Indexer 机制，其原生就是"用降维小 KV 打分"的设计：

- 客户端持久化 Indexer KV 快照（体量约为主 KV 的 1/4）；

- 新请求到达时，客户端获取当前 query 的 embedding（可通过一次轻量服务端调用取回，或使用端侧小模型近似生成）；

- 客户端用 query embedding 与 Indexer KV 打分，选出 top\-k 压缩块；

- 仅上传 top\-k 对应的 C4A/C128 主 KV 条目；

- 服务端在 Decode 过程中若发现真实 attention 分布与客户端选择偏差过大，触发 miss\-and\-fill 补传。

#### 4\.3\.3 KV Cache 生命周期状态机

客户端为每个 PKB 维护如下状态：

- **FRESH**：新写入，未使用；

- **USED**：已至少参与过一次推理，命中记录更新；

- **STALE**：超过 TTL 或距上次使用时间超过阈值，可触发 REFRESH 增量 Prefill；

- **EVICTABLE**：进入淘汰候选，按 LRU / LFU / 用户策略排序；

- **EVICTED**：已从存储中移除，可选发送淘汰通知给服务端用于统计。

状态转换完全由客户端策略决定，服务端不参与调度。

#### 4\.3\.4 安全与可信机制

- 客户端存储的 PKB 采用 AEAD（如 AES\-256\-GCM）加密，密钥由服务端在首次会话时以 KDF 派生并通过安全通道分发；客户端持有加密态，无法篡改内容；

- 每个 chunk 附 HMAC 签名，服务端在接收时校验，校验失败则拒绝并回退全 Prefill；

- 可选支持在服务端 TEE（如 Intel SGX / AMD SEV / ARM CCA）内完成解密与注入，进一步防范中间人；

- 支持"盲上传"模式：多个用户共享前缀 hash 由服务端聚合，但每用户持有独立密钥。

#### 4\.3\.5 引擎无关的抽象接口

本发明定义一组标准接口，使 PKB 可被不同推理引擎接收：

- **PKB 元数据字段**：包含 model\_id、model\_version、tokenizer\_version、layer\_schema\_id、quantization\_scheme、chunk\_layout；

- **KV 注入接口**：定义 `inject_external_kv(pkb_stream, target_kv_pool)` 抽象函数，由各引擎适配层实现；

- **兼容性校验**：服务端在接收前根据元数据校验兼容性，不兼容时回退全 Prefill 或提示客户端刷新。

#### 4\.3\.6 与 PD 分离架构的集成

在 PD 分离部署下：

- 客户端上传的 PKB 直接落入 Prefill 节点的 host pool；

- 经解码后通过 RDMA 直传 Decode 节点的 host pool（direct\-to\-host）；

- 在 Decode 节点，PKB 参与与 HiSparse 兼容的 top\-k on\-demand swap\-in 流程；

- SWA 部分与 c4\_indexer/C128 保持原有服务端内部传输路径，仅 C4 主 KV 走客户端上传路径。

## 五、有益效果

本发明相较现有技术具有以下有益效果：

### 5\.1 效果一：KV Cache 的长期存储，突破服务端老化限制

在现有方案中，服务端 KV Cache 生命周期极短，GPU HBM 中的 KV Cache 通常在秒\~分钟级被 LRU 淘汰，即便扩展至 CPU DRAM 与分布式存储层，也受集群容量与运营策略约束，跨天、跨周复用几乎不可能实现。

本发明将 KV Cache 的存储载体从服务端集群转移至客户端本地（磁盘、端侧 NPU 存储、用户云盘等），使得同一份长上下文对应的 KV Cache 可以在客户端**跨会话、跨天、跨周、跨设备**长期保留。典型场景如：用户对同一份 200K token 财报连续数周进行提问，本地 KV Cache 均可直接复用，无需服务端重新 Prefill。同时，存储成本从服务端摊派转移到客户端自担，服务端边际服务成本大幅下降。

严格地说，本发明并非消除了老化本身，而是将 KV Cache 的老化控制权从服务端转移至客户端，由数据的实际所有者决定其存留策略。

### 5\.2 效果二：客户端对 KV Cache 生命周期的完全感知与主动控制

在现有方案中，KV Cache 的存在状态对客户端完全不可见，客户端只能采取"发出请求 → 被告知 miss → 被迫等待重新 Prefill"的被动模式，导致 TTFT 剧烈波动（从数百毫秒至数秒不等），严重影响交互体验与 SLA 保障。

本发明中，客户端作为 KV Cache 的所有者，对每一条 KV Cache 条目的状态、剩余 TTL、覆盖 token 范围完全自知，由此带来以下可衡量的收益：

- **确定性延迟**：客户端可根据本地 KV Cache 命中情况准确预估 TTFT，为上层应用提供稳定的 SLA；

- **主动预热**：客户端可在用户可能提问前将 KV Cache 提前上传，将网络传输时间与用户思考时间重叠；

- **优雅降级**：当客户端仅持有部分 KV Cache 时，可主动选择"上传部分 \+ 请求服务端补算剩余部分"，避免完全 miss 导致的长时间等待。

### 5\.3 效果三：稀疏与差分上行传输，显著降低网络开销

现有的服务端间 KV 传输方案（如 CacheGen）要求全量传输压缩后的 KV 比特流，客户端场景下若采用同样策略，上行带宽仍会成为瓶颈。

本发明利用 DeepSeek V4 引入的 Lightning Indexer 机制，将稀疏选择从服务端节点内部（HiSparse 的 CPU→GPU swap\-in 路径）延伸至客户端上行链路：

- 客户端持有降维 Indexer KV 快照，在本地对每次 query 进行 top\-k 预打分；

- 仅上传 top\-k 对应的主 KV 块，非选中块保留于客户端不上行；

- 上一次上传的 KV 块作为参考，本次仅上传相对 delta；

- 服务端在真实 attention 分布偏离预测时通过 miss\-and\-fill 协议按需请求补传。

由此，上行带宽相较全量 KV 上行降低 1\~2 个数量级，同时保持生成质量。

### 5\.4 效果四：KV Cache 表征归属用户，实现数据主权与合规友好

在合规敏感场景（如 GDPR 覆盖区、金融、医疗、法律行业）中，用户历史对话与文档对应的 KV Cache 长期驻留于服务提供方，构成数据处理者持有用户数据的事实，涉及数据出境审计、留存义务、数据保护影响评估（DPIA）等合规负担。

本发明将 KV Cache 的持久化载体转移至客户端，服务端仅在处理单次请求的瞬间在受保护内存（可选 TEE 内）持有解密后的 KV 张量，请求结束即释放。结合客户端本地 AEAD 加密与 HMAC 签名机制，实现：

- 用户私有文档的 KV 表征不出客户端 VPC 或个人设备；

- 服务端可自证不留存用户 KV 数据，降低审计负担；

- 支持"一次性推理（ephemeral inference）"模式，用户发问后可自主保证服务端无残留。

### 5\.5 效果五：KV Cache 表征与推理引擎解耦，具备跨引擎、跨服务商可移植性

现有方案中，KV Cache 与特定推理引擎（vLLM、SGLang、TensorRT\-LLM）的内存布局与调度器强绑定，用户上下文一旦落于某推理服务提供方，即形成事实上的 vendor lock\-in，切换服务商需全部重新 Prefill。

本发明定义了引擎无关的 PKB 标准表示格式与 KV 注入抽象接口，只要模型、tokenizer、层结构版本一致，客户端持有的 PKB 可以：

- 在同一服务商内跨不同推理引擎流转（如 vLLM → SGLang）；

- 在不同服务商之间迁移（A 服务商生成、客户端存储、B 服务商接收使用）；

- 支持灾备切换、多云部署、跨版本比对等运维场景。

由此从根本上解除 KV Cache 层面的服务商绑定。

## 六、权利要求书（草案）

### 独立权利要求

6. **一种基于客户端持有 KV Cache 的大语言模型推理方法**，其特征在于，包括以下步骤：

- S1：服务端接收来自客户端的第一次推理请求，完成 Prefill 阶段计算，得到该请求上下文对应的 KV Cache；

- S2：服务端将所述 KV Cache 编码为可携带 KV 表示（PKB），返回给客户端；

- S3：客户端将所述 PKB 及其元数据持久化存储于本地；

- S4：服务端在返回 PKB 后释放对该 KV Cache 的显存与内存占用；

- S5：客户端在后续同上下文推理请求中，基于本地稀疏索引选择部分或全部 KV 块，随请求上传至服务端；

- S6：服务端对上传的 KV 数据完成完整性校验、解码与张量重建，进入 Decode 阶段生成响应。

7. **一种客户端装置**，其特征在于，包括：

- CHK 存储模块，用于持久化保存 PKB 及其元数据；

- 生命周期管理模块，用于维护 PKB 状态机并执行淘汰、刷新策略；

- 稀疏选择模块，用于基于本地 Indexer KV 对 KV 块进行 top\-k 打分选择；

- 差分编码模块，用于对上传数据进行 delta 编码；

- 安全签名模块，用于对上传数据进行 AEAD 加密与 HMAC 签名；

- 传输模块，用于将上传数据与请求 prompt 组合上传至服务端。

8. **一种服务端装置**，其特征在于，包括：

- 完整性校验模块，用于校验客户端上传的 KV 数据；

- PKB 解码模块，用于恢复原始 KV 张量；

- KV 注入模块，用于将恢复的 KV 张量灌入推理引擎的 KV pool；

## 八、可能的规避设计与答审对策

### 8\.1 与 CacheGen 的区分

**审查员可能质疑**：CacheGen 已经实现了 KV Cache 的压缩、分块、流式传输。

**答复要点**：CacheGen 的传输边界严格限定于服务端节点之间（server\-to\-server），存储主体、信任模型、生命周期管理方均为服务端集群运营方。本发明的传输边界跨越服务端与客户端，存储主体为终端用户，信任模型引入了客户端加密与 HMAC 校验，生命周期由用户策略驱动。这些区别构成本质性技术方案差异。

### 8\.2 与 HiSparse 的区分

**审查员可能质疑**：HiSparse 已经实现了 top\-k 稀疏的 KV Cache 加载。

**答复要点**：HiSparse 的稀疏发生在服务端 Decode 节点内部的 CPU→GPU swap\-in 路径，前提是 GPU 已获得完整 attention 打分。本发明的稀疏选择发生在客户端上行链路，在不进行完整前向计算的前提下利用降维 Indexer KV 预判 top\-k，并结合 miss\-and\-fill 兜底机制。二者所处链路层次与技术手段不同。

### 8\.3 与"简单的浏览器缓存"的区分

**审查员可能质疑**：将服务端计算结果缓存于客户端属于常规缓存思路。

**答复要点**：本发明并非缓存最终响应，而是缓存中间张量表示，且该缓存的可用性依赖于严格的模型版本对齐、层结构匹配、量化方案兼容。本发明还包含稀疏选择、差分编码、生命周期状态机、加密签名、跨引擎注入抽象等一系列非显而易见的技术手段，构成完整技术方案。

### 8\.4 关于工程可行性质疑

**审查员可能质疑**：KV Cache 体量过大，客户端持有不切实际。

**答复要点**：本发明特别针对 DeepSeek V4 类采用分层压缩注意力的新一代模型，其 1M token KV Cache 体量已进入客户端可承受区间（V4\-Flash 为 V3\.2 的 7%）。技术可行性以模型架构的最新进展为前提，具备明确的技术背景支撑。
