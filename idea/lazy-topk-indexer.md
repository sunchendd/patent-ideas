# DSA 索引器的时间轴复用：跨解码步惰性 top-k 维护

> 原始想法（一句话级别的点子）。完整过程材料见 `workspace/lazy-topk-indexer/`。

## 痛点
DeepSeek 稀疏注意力（DSA）这条生产主线里，每个注意力层前的 Lightning Indexer 每个**解码步**都要把缓存里全部历史键**读一遍、逐个打分、全量排序**取 top-2048——访存 O(L)，64K~1M 上下文下全缓存读占满 HBM 带宽（MLI 论文原话：长上下文下瓶颈在索引器扫描，不在稀疏注意力）。现有优化（IndexCache/IndexShare 删层复用、MLI 层间流水）全在**层轴**上削重复，保留下来的索引器在每步内仍全量重扫。

## 核心点子
**时间轴**没人用：同一层相邻解码步的 query 只挪一个 token 的距离，上一步的逐键分数和 top-k 绝大部分还有效。给每个缓存键维护「上次精确分数 s_j + 固定范数项 c_j + 累计漂移上界 Δ_j」，用 Lipschitz 界把真实分数锁进区间 [s_j−Δ_j, s_j+Δ_j]，再由全部区间导出门槛必然范围 [L,U]，把键分成**必留/必出/待定**三类——只有区间跨线的"待定键"才读键、算点积。闭合界下选出的 top-k 与全量重扫**严格一致**（无损），每步读键量预估 −91%（64K 上下文）。不改权重、不重训练、单算子替换，且与层轴方案（IndexCache/MLI）正交可叠加。

## 为什么现在能做
学习型稀疏注意力刚成为产业主流（DeepSeek-V3.2/V4、GLM-5、TRT-LLM 2026-11 主干化完整稀疏执行路径），索引器的解码期瓶颈刚被 MLI 论文（arXiv:2611.03768）公开确认，而时间轴方向还没有公开方案——窗口期正开着。
