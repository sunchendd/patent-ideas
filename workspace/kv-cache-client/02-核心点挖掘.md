# 核心点挖掘：客户端持有 KV Cache 的 LLM 推理方法

> 基于 `01-检索报告.md` 的现有技术 landscape，把原始想法反复打磨成经得起审查的核心创新点。
> 产出喂给 `skill/patent-specialist` 撰写 `03-交底书.md`，并对应 `diagrams/*.html`。

---

## 第 0 轮：原始想法

- **一句话痛点**：KV Cache 由服务端独占管理 → 老化快、生命周期不可控、跨会话不可复用、数据主权受限、上行冗余。
- **一句话点子**：把 KV Cache 持久化主体搬到客户端，按需稀疏/差分上传给服务端复用。

---

## 第 1 轮：初版核心点（凭直觉）

1. 客户端缓存 KV Cache。
2. 上传时压缩 KV。
3. 服务端复用上传的 KV 跳过 Prefill。
4. 客户端管理 KV 的过期。

---

## 第 2 轮：检索反馈 —— 哪些已被现有技术覆盖？

| 初版核心点 | 最近现有技术 | 是否已被覆盖 | 保留 / 剔除 / 改写 |
|------------|--------------|--------------|--------------------|
| 1. 客户端缓存 KV Cache | "常规客户端缓存响应" | 部分覆盖（缓存对象不同） | **改写** → 强调缓存的是"中间张量"且依赖严格版本对齐 |
| 2. 上传时压缩 KV | T5 CacheGen | 覆盖（分层量化+算术编码已被发表） | **改写** → 压缩非卖点，"客户端上行稀疏"才是 |
| 3. 服务端复用跳过 Prefill | T1/T2 前缀缓存 | 覆盖（服务端复用是已知） | **剔除** 作为独立卖点，并入系统特征 |
| 4. 客户端管理过期 | 通用 LRU | 部分覆盖 | **改写** → 状态机（FRESH…EVICTED）+ STALE 触发增量 Prefill |

**关键收敛**：单凭"客户端缓存/压缩/复用"任一点都已被现有技术逼近；本发明的**差异化必须落在"存储主体转移到客户端 + 客户端上行链路稀疏预判"的组合**上。

## 第 3 轮：收敛后的核心创新点（最终）

### 核心点 1：可携带 KV 表示（PKB）+ 客户端持久化 —— 存储主体转移
- **是什么**：服务端 Prefill 后将上下文 KV 编码为 PKB 返回客户端，客户端持久化（磁盘/端侧 NPU/用户云盘）；服务端返回后立即释放。
- **为什么现有技术没做**：T1~T5 全部将存储主体限制在服务端集群内部。
- **为什么不是显而易见**：受限于"KV 体量过大无法跨广域传输"的工程常识，直至 DeepSeek V4 把 1M token KV 压到 7%~10% 才首次可行——存在明确的新技术前提。
- **对应**：交底书 §4.1/§4.3.1、权利要求独立项 1（S1~S4）；图见 `diagrams/架构图.html`。

### 核心点 2：客户端上行链路稀疏选择 —— 不做完整前向预判 top-k
- **是什么**：客户端持久化降维 Indexer KV 快照，用当前 query embedding 本地打分选 top-k 压缩块，仅上行选中部分。
- **为什么现有技术没做**：T4 HiSparse 的稀疏发生在服务端 Decode 节点内（已有完整 attention 打分）；无人把稀疏选择前移到无完整前向的客户端。
- **为什么不是显而易见**：利用 DeepSeek V4 Lightning Indexer "用降维小 KV 打分"的原生设计，将其从服务端节点内延伸到客户端广域上行；配合 delta 差分，上行带宽降 1~2 个数量级。
- **对应**：交底书 §4.3.2、从属权利要求 7、8；图见 `diagrams/流程图.html`（S5）。

### 核心点 3：miss-and-fill 兜底闭环 —— 稀疏预测的质量保证
- **是什么**：服务端 Decode 中检测真实 attention 分布与客户端 top-k 选择偏差，超阈值则反向触发客户端补传缺失块。
- **为什么不是显而易见**：把"客户端预测 + 服务端校验 + 反向补传"组成闭环，解决客户端无完整前向带来的预测误差，是稀疏上行方案能落地的前提。
- **对应**：交底书 §4.2 补齐调度模块、从属权利要求 8；图见 `diagrams/流程图.html`（判断菱形 + 虚线回环）。

### 核心点 4：客户端加密签名 + 一次性推理 —— 数据主权
- **是什么**：PKB 在客户端 AEAD 加密、逐 chunk HMAC 签名；服务端仅请求瞬间持解密张量（可选 TEE），请求结束即释放、不留副本。
- **为什么现有技术没做**：服务端独占模型下数据天然驻留服务方，无数据主权诉求；本发明因存储主体转移才需引入客户端信任模型。
- **对应**：交底书 §4.3.4、从属权利要求 9、17。

### 核心点 5：引擎无关的 PKB 抽象 —— 跨引擎/跨服务商可移植
- **是什么**：定义标准 PKB 元数据（model_id/层结构/量化方案/chunk 布局）与 `inject_external_kv` 抽象接口，各引擎适配层实现。
- **为什么不是显而易见**：解耦 KV Cache 与特定引擎内存布局，解除 vendor lock-in，是"存储主体转移"派生的必然需求。
- **对应**：交底书 §4.3.5、从属权利要求 11、12。

## 防御性扩展清单

- [x] **维度扩展**：从"延迟"扩展到 TTFT / 上行带宽 / 服务端边际成本 三指标。
- [x] **场景扩展**：长上下文财报、合规敏感（GDPR/金融/医疗/法律）、跨设备同步。
- [x] **层级扩展**：客户端层 + 传输层 + 服务端注入层 + 引擎适配层。
- [x] **稳定性扩展**：兼容性校验失败回退全 Prefill、STALE 触发增量 Prefill。
- [x] **自动化扩展**：按网络带宽在"仅上传 prompt 重算"与"上传 KV 跳过重算"间自适应切换。
- [x] **并发扩展**：多用户盲上传（前缀 hash 聚合 + 各自密钥）。
- [x] **组合扩展**：与 PD 分离架构集成（PKB 直接落入 Prefill 节点 host pool，RDMA 直传 Decode 节点）。
